DEMETRIOUS: The flash message system relies on sessions to support the Post-Redirect-Get pattern. Because a redirect triggers a new HTTP request, sessions allow us to store messages on the server so they persist between requests.

Here's how I set up sessions and flash messages in my server.js:

import session from 'express-session';
import flash from './src/middleware/flash.js';

// Set up session management
app.use(session({
    secret: SESSION_SECRET,
    resave: false,
    saveUninitialized: true,
    cookie: { maxAge: 60 * 60 * 1000 }
}));

// Use flash message middleware
app.use(flash);

And here's the actual flash middleware I wrote in src/middleware/flash.js that handles storing and retrieving messages:

const flashMiddleware = (req, res, next) => {
    req.flash = function(type, message) {
        if (!req.session.flash) {
            req.session.flash = { success: [], error: [], warning: [], info: [] };
        }
        if (type && message) {
            if (!req.session.flash[type]) {
                req.session.flash[type] = [];
            }
            req.session.flash[type].push(message);
            return;
        }
        const allMessages = req.session.flash || { success: [], error: [], warning: [], info: [] };
        req.session.flash = { success: [], error: [], warning: [], info: [] };
        return allMessages;
    };
    next();
};

So the way it works is when I call req.flash('success', 'Organization added!') in a controller, it stores that message in the session before the redirect happens. Then when the next page loads, the EJS template calls flash() which retrieves all the messages from the session and immediately clears them so they only show once. That "read and delete" behavior is what makes them flash messages, they appear exactly once and then they're gone. Without sessions there would be no way to carry that message across the redirect since HTTP is stateless by nature.

DEMETRIOUS: Here is the server-side validation I implemented for the organization form using the express-validator library:

const organizationValidation = [
    body('name')
        .trim()
        .notEmpty().withMessage('Organization name is required')
        .isLength({ min: 3, max: 150 }).withMessage('Organization name must be between 3 and 150 characters'),
    body('description')
        .trim()
        .notEmpty().withMessage('Organization description is required')
        .isLength({ max: 500 }).withMessage('Organization description cannot exceed 500 characters'),
    body('contactEmail')
        .normalizeEmail()
        .notEmpty().withMessage('Contact email is required')
        .isEmail().withMessage('Please provide a valid email address')
];

To break down my logic:
For the name, I first use .trim() to prevent users from submitting only whitespace. I then enforce a length constraint of 3 to 150 characters. I kept the minimum length requirement strictly on the server side so I can verify that my backend validation is functioning independently of any client-side browser restrictions.
For the description, I also trim and check for non-empty input, while capping it at 500 characters to ensure the data aligns with my database schema and UI limitations.
For the contactEmail, I utilize normalizeEmail() to standardize the format, followed by isEmail() to ensure the input is a valid email structure. I prioritized this validation because storing malformed emails would prevent future communication with those contacts.
I chose express-validator over manual logic because it keeps the rules clean and declarative. By using it as middleware, I can simply drop the organizationValidation array into my routes, ensuring the validation runs automatically before the controller processes any database operations.

Here's the insight: normalizeEmail() transforms the input before the other checks run.
